# 3. 说明白

> 话从我流到对方。核心只有一件事：**把脑子里的网，拆成嘴里的线。**

<a id="h-27f1b14ec85c"></a>

## 3.1 结构化表达（底层功夫）

> 这一节是后面所有表达场景的地基。**看不懂后面的，回来看这里。**

<a id="h-52ed83887365"></a>

### 3.1.1 四个万能结构

**结构 A：先结论后展开（最常用）**

```
结论 → 理由 → 数据/例子 → 建议
```

> "建议这版先不做多端适配（结论）。
> 因为现在 90% 的访问来自 PC（理由），移动端上月只有 340 个 UV（数据）。
> 建议先把 PC 端体验打磨好，移动端排到 Q4（建议）。"

**结构 B：3W**

```
What（说什么）→ Why（为什么）→ How（怎么做）
```

适合：讲一个新东西、做一次分享。

**结构 C：FPA —— 事实 → 问题 → 建议**

```
事实（发生了什么）→ 问题（影响是什么）→ 建议（怎么办）
```

适合：**报告坏消息。** 因为它天然地把"发生了什么"和"谁的责任"分开了。

> "测试昨天发现登录模块有并发问题（事实）。
> 按现在的修复速度，周四上不了（问题）。
> 我建议两个选项：A 是延到下周二，B 是这版先关掉这个入口（建议）。"

**结构 D：用户视角**

```
场景 → 动机 → 阻碍 → 期望结果
```

适合：讲需求、做评审、说服业务方。

> "采购员在月底对账的时候（场景），想快速核对上月所有订单（动机），
> 但现在要一张张翻，一次对账要两小时（阻碍）。
> 我们想让他一次导出、十分钟对完（期望结果）。"

<a id="h-fa68c0fbfd85"></a>

### 3.1.2 SCQA（麦肯锡的开场）

```
Situation 情景 → Complication 冲突 → Question 疑问 → Answer 答案
```

> "我们的指标体系今年要上线（S）。
> 但商品数据只录了三分之一，按这个速度年底完不成（C）。
> 那要怎么保证按时上线（Q）？
> 我建议把商品分三批，核心品类先录，长尾品类明年补（A）。"

**SCQA 的威力在 C。** 没有冲突，对方就没有听下去的理由。

<a id="h-2379ab15d274"></a>

### 3.1.3 PREP（最快的一个）

```
Point 观点 → Reason 理由 → Example 例子 → Point 重申观点
```

> "我建议延期一周（P）。
> 因为核心的支付链路还有 3 个高危 bug（R）。
> 上一次我们带 bug 上线，结果两天后紧急回滚，反而花了更多时间（E）。
> 所以我建议延一周，一次做稳（P）。"

**开会临时被点名，用这个。** 四句话，20 秒。

<a id="h-e9e4831b77c9"></a>

### 3.1.4 结构怎么选

| 我要干嘛 | 用 |
|---|---|
| 汇报进展 | A：先结论后展开 |
| 报坏消息 | C：FPA |
| 讲需求 | D：用户视角 |
| 正式提案 | SCQA |
| 临时被点名 | PREP |
| 做分享 | B：3W |

**记不住就用 A。** 先说结论，永远不会错。

<a id="h-6a774d06727b"></a>

### 3.1.5 去情绪化表达

| 别说 | 改成 |
|---|---|
| "他们又拖了" | "对方的反馈比约定晚了 3 天" |
| "这需求根本没法做" | "按现在的方案，需要 X 人天，超出这版排期" |
| "我早就说过了" | "我们上次讨论时提到的风险出现了，现在的情况是……" |
| "这不是我的问题" | "这个环节的负责人是 X，我可以帮忙拉他一起看" |

**三条铁律：**
1. 说事实，不说感受
2. 说逻辑，不说抱怨
3. 说"现在怎么办"，不说"当初谁的错"

<a id="h-b9a72c0c5a01"></a>

### 3.1.6 可视化表达

能画就别说，能列就别写成段落。

| 内容形态 | 用 |
|---|---|
| 并列的几件事 | 列表 |
| 多个维度对比 | 表格 |
| 层级关系 | 树状/缩进 |
| 有先后顺序 | 流程图 |
| 有条件分支 | 判断树 |

<a id="h-ea17fe788133"></a>

### 3.1.7 表达质量自检（发出去之前过一遍）

- [ ] 有没有一句话结论？
- [ ] 信息有没有分类？
- [ ] 每句话是不是只有一个意思？
- [ ] 是不是从**对方**的角度组织的？
- [ ] 有没有明确的下一步？

**五条都打勾再发。**

## 3.2 汇报

<a id="h-6eb77dbc5881"></a>

### 先问自己 3 句

1. 这次汇报，我要的是**知情**、**决策**，还是**资源**？
2. 领导听完，**他能拿去跟他老板说什么**？
3. 有没有坏消息？**坏消息必须在前三句里出现。**

<a id="h-9fe7a88e18a7"></a>

### 走哪条路

| 我要的是 | 走 |
|---|---|
| 让他知情 | 路线 A：进展型汇报 |
| 让他拍板 | 路线 B：决策型汇报（见 3.3 提案） |
| 要人要钱要时间 | 路线 C：资源型汇报 |
| 有坏消息 | 路线 D：坏消息汇报（见 7.1） |

<a id="h-b3fbc6c54277"></a>

### 路线 A：进展型汇报

万能公式：

```
结论 + 关键数据 + 风险 + 下一步
```

> "本周版本按计划上线了，核心指标没有异常（结论）。
> 订单转化 3.2%，比上周 +0.4 个点（数据）。
> 有一个风险：下周有节假日，可用工时少三天（风险）。
> 下周重点是把 X 功能的验收做完（下一步）。"

**四句话。不要流水账。**

<a id="h-52f7bff1c916"></a>

### 路线 C：资源型汇报

```
现状 + 缺口 + 我已经做的努力 + 具体请求
```

> "指标标准化的数据录入，目前完成 33%（现状）。
> 按现在的投入，年底只能到 60%，差 40%（缺口）。
> 我已经把录入模板简化了，单条耗时从 5 分钟降到 2 分钟（我的努力）。
> 想请您帮我跟编辑部的负责人对一下，看能不能再加一个人（具体请求）。"

**"我已经做的努力"这一句不能省。** 没有它，你就是在甩包袱。

<a id="h-42042606adbc"></a>

### 汇报的完整框架（正式场合）

| 板块 | 回答什么 |
|---|---|
| 解决问题的必要性 | 什么痛点？为什么现在解决？能解决到什么程度？ |
| 核心策略手段 | 用什么打法？有什么行业洞察？有成功案例吗？ |
| 关键数据指标 | 最核心的 3-4 个指标是什么？现在多少？对比往期/竞品如何？ |
| 思考与沉淀（可选） | 哪些经验可复用？哪些教训要规避？ |

<a id="h-30fbe83370ec"></a>

### 频次与轻重

| 场合 | 特点 |
|---|---|
| 年度规划 | 最重，要有战略高度和数据支撑 |
| 季度/月度 | 重结果，要有对比 |
| 周会 | 重节奏，突出变化和风险 |
| 日常同步 | 最轻，一两句话，随手发 |
| 复盘会 | 重教训，别只讲好的 |

**重点汇报要像广告**：让老板在很短时间内看懂、认同、达成共识。
**普通汇报可以略长**：补上你的思考过程，让老板看到你花了功夫。
**但任何汇报都切忌流水账。**

<a id="h-aa9c601b63cf"></a>

### 别做这些

- ❌ 从头讲到尾，结论放最后 —— 领导听到一半就走神了
- ❌ 只报喜不报忧 —— 一次隐瞒，信任归零
- ❌ 只讲"做了什么"不讲"结果怎样" —— 那是工时记录，不是汇报
- ❌ 报了问题不给方案 —— 见 3.3

## 3.3 提案 / 请示

> **请示工作，必带方案。** 让领导做选择题，不做问答题。

<a id="h-3b73c957ecf9"></a>

### 先问自己 3 句

1. 我准备了**几个**方案？（少于 2 个，别去）
2. 我**推荐**哪一个？为什么？
3. 对方拍板之后，**谁去执行**？

<a id="h-56189adb22b3"></a>

### 标准结构

```
1. 一句话问题
2. 方案 A：做法 / 成本 / 风险
3. 方案 B：做法 / 成本 / 风险
4. 我的推荐 + 理由
5. 需要您决定的是：______
```

**第 5 条一定要写出来。** 把"你要决定什么"明确画出来，领导才知道该说什么。

> 可以直接抄：
> "有件事想请您定一下。
> 问题是：X 功能开发量超预期，按现在的排期，这版做不完。
> 方案 A：砍掉子功能 a，本版按时上，下版补齐。成本是客户看不到完整能力。
> 方案 B：整体延一周。成本是跟业务方承诺的时间要改。
> 我倾向 A，因为客户当前最在意的是 b 功能，a 可以后补。
> 需要您定的是：走 A 还是 B。"

<a id="h-2873081e37b9"></a>

### RIDE 说服模型（提案的加强版）

| 字母 | 讲什么 |
|---|---|
| **R** Risk 风险 | 不做会怎样？现在的困境是什么？ |
| **I** Interest 利益 | 做了能得到什么？ |
| **D** Difference 差异 | A 方案和 B 方案的区别在哪？ |
| **E** Effect 影响 | 对全局有什么影响？**适当补充一些缺点。** |

**"适当补充缺点"是这个模型最值钱的一条。** 只说好处，对方会自己找缺点；你主动说出来，反而显得可信。

<a id="h-4b09d7b6dccd"></a>

### 政治可行性评估（重要提案必做）

每个提案背后，补一页只给自己看的：

| 问 | 答 |
|---|---|
| 谁会损失？ | |
| 谁会得利？ | |
| 谁能帮我站台？ | |
| 对方说"好"的最低条件是什么？ | |

再准备**两个版本的报价**：
- **保底版**：最小可接受方案，对方一定能点头
- **野心版**：你真正想要的

先抛野心版，退到保底版。

<a id="h-a9bfcb302c6a"></a>

### 别做这些

- ❌ 只有一个方案 —— 那不叫提案，叫通知
- ❌ 方案之间没有实质差别 —— 领导会看出你在演戏
- ❌ 不给推荐 —— "您看怎么办"等于把球又踢回去了
- ❌ 不写"需要您决定什么" —— 会议开完，什么都没定

## 3.4 需求评审

<a id="h-08ef0b452713"></a>

### 先问自己 3 句

1. 这次评审，我要的是**通过**，还是**收意见**？
2. 最可能反对的是谁？他会反对**哪一点**？
3. 哪些是**已定**的，哪些是**待议**的？（开场就要说清）

<a id="h-f7708b213983"></a>

### 开场三句（定调子）

> "今天这个需求的核心价值是【一句话】。
> 已经定了的是【A、B】，今天主要想议的是【C】。
> 预计 40 分钟，最后 10 分钟留给待确认项。"

**开场把"待议范围"框住，会就不会散。**

<a id="h-53b1c7f8d760"></a>

### 讲需求的顺序

```
一句话定位 → 用户场景链 → 原型路径 → 技术要点 → 风险 & 假设
```

| 板块 | 讲什么 | 讲给谁听 |
|---|---|---|
| 一句话定位 | 这个需求解决谁的什么问题 | 所有人 |
| 用户场景链 | 用户从 A 到 B 会经历什么 | 业务方 |
| 原型路径 | 界面怎么走 | 设计、测试 |
| 技术要点 | 触发条件、系统行为、边界、异常分支 | 开发 |
| 风险 & 假设 | 我假设了什么，哪里可能崩 | 领导、测试 |

<a id="h-3a7e90d2645e"></a>

### 对技术讲需求的五件套

**每一个功能点，都要讲全这五样：**

1. **触发条件** —— 什么情况下会发生
2. **系统行为** —— 发生后系统做什么
3. **边界条件** —— 极值、空值、超长、并发
4. **异常分支** —— 失败了怎么办
5. **需技术确认的点** —— 我不确定的，请你判断

**第 5 条是保命的。** 主动标出"我不确定"，比事后被质问"你怎么没写"强一百倍。

> 详见 [7.18 需求没写清被质问](07_麻烦现场_V1_2026-11-01.md#h-91536cba13da)

<a id="h-0ea5c6918c4c"></a>

### 提案文档模板（简版）

```
项目名称：
日期 / 提交人：

一、概述          目的和预期成果
二、主要需求      需求1 / 需求2 / ……
三、预期目标      完成后达到什么
四、风险与挑战    顶层风险列表
五、时间线        主要里程碑
六、下一步        评审后的行动
```

<a id="h-007b0ab6e416"></a>

### 提案文档模板（完整版，正式项目用）

```
一、引言          背景 / 目标 / 范围（含"不在范围内"的部分）
二、项目描述      需求概述 / 功能需求 / 非功能需求
三、初步设计      技术框架 / 设计考虑（架构图、数据流图）
四、风险评估      潜在风险 / 缓解策略
五、时间线        详细时间表 / 关键里程碑
六、预算估算      成本初估
七、附件          背景材料 / 术语表
八、审阅与反馈    审阅流程 / 反馈期限 / 下一步行动
```

> **"范围"里一定要写清"哪些不在这次讨论范围内"。** 这一句能省掉一半的跑题。

<a id="h-0c247a468768"></a>

### 方案确认（评审后，跟需求方对齐）

九步话术：

1. **清晰陈述方案** —— "根据您提的问题，我们的方案是……"
2. **解释理由和好处** —— "推荐这个方案是因为……，它能帮您……"
3. **用大白话** —— 不用术语，除非确定对方懂
4. **给步骤** —— "首先……接着……最后……"
5. **邀请提问** —— "有哪里不清楚或者有疑虑的吗？"
6. **确认细节** —— "关于 X 的部分，是否符合您的期望？"
7. **强调合作** —— "我们希望跟您密切配合，一起做到最好"
8. **提供选择** —— "您可以在 A 和 B 之间选，两个都可行"
9. **总结并请求确认** —— "所以我们现在是按 X 来推进，您确认一下我们理解一致？"

**第 9 步不能省。** 口头"嗯"不算，最好落成文字。

<a id="h-c9653fff9c01"></a>

### 别做这些

- ❌ 上来就翻原型 —— 没人知道为什么要做
- ❌ 把"待议"讲成"已定" —— 后面一定会翻车
- ❌ 会上被问住就当场改方案 —— 说"这个我回去确认"
- ❌ 会后不发纪要 —— 详见 [6.6 主持会议](06_给反馈_V1_2026-11-01.md#h-53faf86d8e27)

## 3.5 即兴发言

> 被突然点名。你有 5 秒钟准备时间。

<a id="h-8fb1279658fb"></a>

### 先问自己 1 句

**"他点我，是想听什么？"**

| 他想听 | 你说 |
|---|---|
| 一个态度 | 表态 + 一个理由 |
| 一个信息 | 事实 + 数字 |
| 一个判断 | PREP |
| 打个圆场 | 认同 + 补充一个角度 |

<a id="h-8d18dc4a32f4"></a>

### 万能公式：PREP

```
观点 → 理由 → 例子 → 重申观点
```

20 秒说完，比说 3 分钟废话强。

<a id="h-7ac4f09a2196"></a>

### 如果真的没准备

> 可以直接抄：
> "这块我了解的信息不全，先说我知道的部分：【说你确定的那一点】。
> 至于【不确定的那部分】，我会后跟 X 确认一下，今天下班前给大家同步。"

**承认信息不全，不丢人。当场编，才丢人。**

<a id="h-6353c5f807d5"></a>

### 三句话结构（最小可用）

不管什么场合，这三句都能撑住：

1. 发生了什么
2. 问题/影响是什么
3. 我的建议是什么

<a id="h-853b0bf86d50"></a>

### 别做这些

- ❌ "这个我不太清楚" 然后就没了 —— 给一个跟进承诺
- ❌ 铺垫五句才说重点 —— 直接说结论
- ❌ 当场承诺时间点 —— "我确认后给您准信"

## 3.6 晋升答辩

> 答辩不是汇报工作，是**证明你已经在下一个层级干活了**。

<a id="h-c38c5d0f15ae"></a>

### 先问自己 3 句

1. 下一个层级的核心要求是什么？（不是"做得多"，是"担得起"）
2. 我有哪一件事，**只有我能做成**？
3. 评委最可能挑战我哪一点？

<a id="h-953c96d7ddff"></a>

### 结构

```
1. 我负责什么（一句话，带规模数字）
2. 三件代表作（每件用 STAR）
3. 我的方法论沉淀（可复用的）
4. 我对业务的判断（体现高度）
5. 下一步我想干什么
```

<a id="h-51f947fbaf06"></a>

### STAR 讲一件事

| 字母 | 讲什么 | 常见错误 |
|---|---|---|
| **S** Situation | 当时什么情况 | 讲太长 |
| **T** Task | 我的目标是什么 | 讲成"领导让我做" |
| **A** Action | **我**做了什么 | 讲成"我们做了什么" |
| **R** Result | 结果如何，有数字 | 没有数字 |

**A 部分必须是"我"。** 评委在找的是你个人的贡献，不是团队的。

**R 部分必须有数字。** 没有数字的结果，评委会当成没有结果。

<a id="h-734c64123e9b"></a>

### 加分的三个动作

1. **主动讲失败** —— 讲一件没做成的，以及你从中改了什么。评委会认为你是真实的。
2. **讲方法论** —— "这件事之后，我把它沉淀成了一套 X 流程，现在组里三个人都在用。" 这证明你的影响力超出了自己的工位。
3. **讲判断** —— "我认为明年这块业务的关键变量是 X。" 这证明你在用更高的视角看问题。

<a id="h-5665744e797f"></a>

### 别做这些

- ❌ 按时间顺序流水账 —— 按"能力项"组织
- ❌ 全是"我们" —— 评委分不清你干了什么
- ❌ 只讲苦劳 —— 加班时长不是能力
- ❌ 回避失败 —— 评委会认为你没有反思能力
